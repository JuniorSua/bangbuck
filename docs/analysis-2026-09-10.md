The assessment below records the findings before those changes.

Compared the working snapshot captured September 10 with the committed September 5 snapshot, recalculated both tiers, inspected the served page HTML and component code, checked the public source pages, and ran the tests and production build. No ranking settings or application code were changed.

These are voted ratings, so the zero-vote exclusion correctly allows them. DeepSWE's source remains [Datacurve's benchmark](https://deepswe.datacurve.ai/).

High-power qualifiers grow from 3 to 7; everyday qualifiers grow from 18 to 23. All five Astra efforts now receive Craft scores. ## How strongly to interpret the new answer

Both winning Astra efforts inherit the **max-effort** WebDev rating. Their approximately 88.8% Craft is an Elo-derived expectation against the reference rating, not a measured vote percentage for low or medium effort. The current matching policy permits this, but the headline needs to disclose it.

The arithmetic has a substantial cushion once Astra clears Craft. Holding the current reference and competitors fixed, assigning Astra medium only the minimum passing 75% Craft still gives it 2.33× Opus high's score. Assigning Astra low only 70% Craft gives it 1.74× Sol high's score. These are conditional scenarios, not evidence that those effort levels actually clear the gate.

That evidence can be approximated. Four families have more than one rated effort on WebDev, and their Elo moves 8.4–23.3 points per effort step (median 20.4). Rating each lower Astra effort at max minus drift × steps:

| Drift per step | High power | Everyday |
| --- | --- | --- |
| 0 (current policy) | Astra medium, 1.41× | Astra low, 2.01× |
| 20.4 (observed median) | Astra medium, 1.40× | Astra low, 1.93× |
| 40 (≈1.7× steepest observed) | Astra medium, 1.38× | Astra low, 1.83× |
| 60 | Astra high | Sol high |

Both crowns survive every drift the data has shown, so the nearest-effort policy stays and the borrowing is disclosed rather than penalised. `lib/refresh.test.ts` pins the 20.4 / 40 / 60 cases.

Astra medium remains the high-power winner in a 100-combination sweep of token penalty, step penalty, and Craft weight. Everyday is more sensitive: the same sweep produces either Astra low or Gemini 3.7 Flash medium. Do not claim universal stability for the everyday answer.

Astra medium's Ship confidence interval is approximately 70.2–75.4%, crossing the 72.5% high-power floor. It qualifies by its point estimate. Astra low's 65.7–68.3% interval sits above the 65% everyday floor. The page should explain this difference without treating marginal confidence bounds as a proven failure.

## Improvements in priority order

1. **Put evidence provenance on the winner card.** `components/WinnerCard.tsx` prints an unqualified Craft percentage and claims humans prefer the selected effort's work. Add “Craft estimated from Astra max,” the source entry, vote count, and rating interval. Carry the same disclosure into the sticky answer and category cards. Offer an optional “direct effort matches only” view; among current qualifying exact matches, Opus high leads high power and Sol xhigh leads everyday. Keep the existing policy as an explicit choice rather than silently changing it.

2. **Make refresh comparisons cover the inputs that change the answer.** `lib/diff.ts` compares only DeepSWE configuration changes and four measured fields. Comparing these two snapshots returns **“No changes.”** Add Arena additions/removals, rating availability and effort-match changes, reference movement, qualifier transitions, and before/after winners for each tier. This refresh is a concrete regression case: unchanged DeepSWE data, two new winners.

3. **Separate historical fixtures from current-snapshot tests.** Thirty of 89 tests fail. Many still require Opus or Sol to win, or Astra to remain unrated. Preserve those historical situations in fixed fixtures, and test current data separately for valid joins, qualification rules, numerical integrity, and the intentional new results. Merely replacing every old expected number would leave the next refresh equally brittle. Update the README's opening recommendation, coverage counts, tie discussion, and obsolete penalty claims.

4. **Explain the score accurately.** The hero says “the cheapest survivor wins,” yet everyday's winner costs more than Gemini. Use “best balance of capability, measured cost, output tokens, and agent steps.” Label Craft as estimated WebDev preference against the board reference; “code worth keeping” overstates what a WebDev preference board establishes about general code quality. Show the normalized token/step baselines in the advanced formula so readers can reproduce the displayed numerical score.

5. **Make the selected tier and freshness visible beside the answer.** The tier switch currently comes after the winner and six category cards. Move the tier selector next to the answer, with the active floors visible. Add a short “What changed” strip. The header currently says September 3 because it uses only DeepSWE's generation date, hiding the newer Arena evidence; distinguish benchmark date from September 10 snapshot capture.

6. **Show uncertainty and ties where they matter.** Add “Ship interval crosses your floor” beside marginal qualifiers. The “Best code” category currently selects Astra medium or low because equal inherited Craft scores are resolved by ranking order; show the shared family rating or mark the tie instead of implying an effort-specific quality win. Make borrowed-rating explanations available without relying on a tiny hover-only tilde.

7. **Fix the sensitivity report's interval boundaries.** `craftFloorRegimes()` evaluates at each Craft score, where equality still qualifies, and extends that winner through the following interval. It currently reports Astra winning up to 100% Craft, although `computeRanking(..., craftFloor: 0.9)` correctly returns no winner. Evaluate the open intervals correctly, represent the empty region, and test interval interiors as well as boundaries. This affects the analysis script; the main page's direct ranking calculation is correct.

8. **Keep rejection explanations tied to the active settings.** `bestExcludedOnCraft` uses a fixed everyday Ship floor and compares Craft with the winner rather than checking the actual failure reason. At the high-power tier with Craft lowered to 60%, it still names Luna max as the Craft exclusion even though Luna passes Craft and fails Ship. The slider's fixed “under 65%” Luna comeback claim is also false for the default high-power tier. Derive these explanations from the current gates.

Additional usability work: expose output tokens and steps in a mobile row detail (the table hides both on phones), add keyboard access to chart point inspection, and make row failure reasons explicit in text. The measured-but-unrated radar also needs to check Ship before saying a hypothetical Craft rating would take the crown; it currently has no visible rows, but the next unrated release can reactivate that issue.

## Validation and limits

- Production build and TypeScript checks passed with `npm run build:check`.
- Tests: 59 passed, 30 failed; failures were reviewed and not suppressed.
- Both tier rankings, category winners, old/new qualifiers, conservative Craft scenarios, and sensitivity counterexamples were calculated directly from the project code.
- The local server returns the new Astra answer in its HTML.
- A browser was unavailable through the computer-use tool, so visual layout, touch behavior, and keyboard interactions were not verified in a browser. Layout recommendations above are based on the rendered HTML and component structure.

Recommended first implementation batch: winner provenance, complete refresh diffs, fixture-based tests, and accurate tier/freshness copy. Preserve the owner's current penalty settings while addressing these evidence and correctness problems.
